# GraphRAG روی Hetionet (نسخهٔ فارسی)

این صفحه خلاصهٔ فارسی [README انگلیسی](../../README.md) است و بخش ارزیابی آن کامل ترجمه شده است. فهرست کامل قابلیت‌ها و تصویرها در نسخهٔ انگلیسی آمده است. اگر دو نسخه با هم فرق داشتند، نسخهٔ انگلیسی معتبر است.

## معرفی

این مخزن پروژهٔ کارشناسی **امیرحسین خوشبخت** و **علی رحیمی** در دانشگاه صنعتی شریف، به راهنمایی دکتر حمید بیگی است: یک سیستم تولید پاسخ مبتنی بر بازیابی (RAG) که به سؤال‌های زیست‌پزشکی پاسخ می‌دهد. شواهد را به‌جای متن، از یک گراف دانش بازیابی می‌کند.

گراف دانش مورد استفاده [Hetionet v1.0](https://het.io) است. این گراف داده‌های ۲۹ منبع عمومی زیست‌پزشکی را در ۴۷٬۰۳۱ گره از ۱۱ نوع (ژن، دارو، بیماری، بافت، علامت، عارضهٔ جانبی، مسیر زیستی، فرایند زیستی و غیره) و ۲٬۲۵۰٬۱۹۷ یال از ۲۴ نوع رابطه جمع کرده است. نمونهٔ این رابطه‌ها: «دارو بیماری را درمان می‌کند»، «بیماری با ژن مرتبط است» و «دارو به ژن متصل می‌شود». سیستم Hetionet را به‌صورت یک گراف بی‌جهت NetworkX بارگذاری می‌کند و برای هر سؤال این کارها را انجام می‌دهد:

1. موجودیت‌هایی را که در سؤال آمده‌اند و نوع رابطه‌ای را که سؤال دربارهٔ آن است پیدا می‌کند.
2. با یکی از چند روش جست‌وجوی گراف، زیرگرافی را اطراف آن موجودیت‌ها بازیابی می‌کند.
3. زیرگراف را به متن زمینه تبدیل می‌کند.
4. این متن را به یک تولیدکنندهٔ قالبی یا به API یک مدل زبانی می‌دهد تا پاسخ ساخته شود.

مخزن این بخش‌ها را هم دارد:
- رابط وب Flask
- ماژولی برای ساخت گراف دانش از متن آزاد، نشانی وب یا صفحهٔ ویکی‌پدیا
- پشتیبانی بخشی از سؤال‌های فارسی
- ارزیابی قابل بازتولید در مقایسه با یک RAG معمولی مبتنی بر بازیابی برداری (بخش [ارزیابی](#ارزیابی))

در آن ارزیابی، خط مبنا در سؤال‌های تک‌رابطه‌ای خیلی بیشتر از جواب‌های درست را بازیابی می‌کند. در سؤال‌های دومرحله‌ای، بهترین روش GraphRAG کمی جلوتر است.

## معماری

نمودار معماری در [README انگلیسی](../../README.md#architecture) آمده است. مراحل اصلی خط پردازش:

- **استخراج کلیدواژه:** با spaCy، قاعده‌های تشخیص نماد ژن و یک واژه‌نامهٔ فارسی‌به‌انگلیسی.
- **تشخیص نوع سؤال:** با قاعده‌های الگومحور که هر الگو را به نوع رابطه‌های Hetionet نگاشت می‌کند.
- **تطبیق موجودیت:** تطبیق دقیق نام، کلیدواژهٔ نوع گره یا زیررشته روی ۴۷ هزار گره.
- **بازیابی از گراف:** جست‌وجوی هوشمند هدایت‌شده با نوع رابطه، BFS، DFS، کوتاه‌ترین مسیر، همسایه‌ها، PageRank و روش‌های ترکیبی (hybrid، ensemble، adaptive).
- **ساخت متن زمینه:** گره‌ها، رابطه‌ها و مسیرها در یکی از چند سبک متنی نوشته می‌شوند.
- **تولید پاسخ:** با قالب‌های محلی یا مدل‌های OpenAI، Anthropic، Google و Hugging Face.

ماژول‌های اصلی:

- `graphrag_service.py`: خط پردازش اصلی، شامل استخراج کلیدواژه، تشخیص نوع سؤال (`analyze_question_intent`)، تطبیق موجودیت (`match_tokens_to_nodes`)، روش‌های بازیابی (`RetrievalMethod`، `retrieve_information`)، ساخت متن زمینه (`create_context_text`) و تولید پاسخ (`GenerationModel`، `generate_answer`).
- `enhanced_graphrag_service.py` و `enhanced_context_generator.py`: سرویس گسترش‌یافته با بازیابی و تشخیص جامعهٔ قابل‌تنظیم و قالب‌های غنی‌تر برای متن زمینه.
- `node_lookup_system.py`: نگاشت شناسهٔ گره‌های Hetionet به نام، نوع و توضیح کوتاه برای نمایش.
- `text_to_graph_service.py`، `url_extractor.py`، `wikipedia_extractor.py`: ساخت گراف از متن با استخراج موجودیت و رابطه به روش قاعده‌محور، با spaCy یا با مدل زبانی.
- `persian_normalizer.py`، `persian_models.py`: نرمال‌سازی متن فارسی و نگاشت اصطلاحات.
- `web_app.py` به همراه `templates/` و `static/`: رابط وب Flask و API مبتنی بر JSON.
- `rebuild_graph.py`: ساخت گراف NetworkX از فایل‌های Hetionet.
- `evaluation/`: تولید سؤال‌ها، خط مبنای RAG برداری و اسکریپت اجرای ارزیابی.

## نصب

به Python 3.10 یا جدیدتر نیاز دارد. پروژه با Python 3.13 روی ویندوز توسعه داده و تست شده است.

</div>

```bash
git clone https://github.com/amirhosseinkho/graphRAG.git
cd graphRAG
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt
python -m spacy download en_core_web_sm

# Download Hetionet v1.0 and build hetionet_graph.pkl
python scripts/download_data.py
```

<div dir="rtl">

اسکریپت `scripts/download_data.py` این مراحل را انجام می‌دهد:
1. فایل‌های `hetionet-v1.0-nodes.tsv` و `hetionet-v1.0-edges.sif.gz` را از مخزن رسمی [hetio/hetionet](https://github.com/hetio/hetionet) دانلود می‌کند.
2. فایل یال‌ها را در `edges.sif` از حالت فشرده خارج می‌کند.
3. `rebuild_graph.py` را اجرا می‌کند تا فایل `hetionet_graph.pkl` در ریشهٔ مخزن ساخته شود.

هیچ‌کدام از این فایل‌ها در git نگه‌داری نمی‌شوند. اگر فایل گراف وجود نداشته باشد، سرویس از یک گراف نمونهٔ کوچک داخلی استفاده می‌کند.

تولید پاسخ با مدل زبانی اختیاری است و تولیدکننده‌های قالبی بدون اینترنت کار می‌کنند. برای استفاده از API، کلید مربوط را پیش از اجرای برنامه تنظیم کنید:

</div>

```bash
export OPENAI_API_KEY=...          # Windows PowerShell: $env:OPENAI_API_KEY="..."
```

## استفاده

**رابط وب**

</div>

```bash
python web_app.py
```

<div dir="rtl">

سپس http://localhost:5000 را باز کنید. در این رابط می‌توانید:
- روش بازیابی، سبک متن زمینه و مدل تولید پاسخ را انتخاب کنید.
- زیرگراف بازیابی‌شده را ببینید.
- گراف آپلود کنید یا از متن یا نشانی وب گراف بسازید.
- گراف فعال را عوض کنید.

**پایتون**

</div>

```python
from graphrag_service import GraphRAGService, RetrievalMethod, GenerationModel

service = GraphRAGService()  # loads hetionet_graph.pkl from the working directory
result = service.process_query(
    "Which compounds treat hypertension?",
    RetrievalMethod.INTELLIGENT,  # or BFS, DFS, SHORTEST_PATH, NEIGHBORS, ADAPTIVE, ...
    GenerationModel.SIMPLE,       # template-based; e.g. OPENAI_GPT_4O_MINI needs an API key
)
print(result["matched_nodes"])
print(result["context_text"])
print(result["answer"])
```

<div dir="rtl">

**API تحت وب**

</div>

```bash
curl -X POST http://localhost:5000/api/process_query \
     -H "Content-Type: application/json" \
     -d '{"query": "Which compounds treat hypertension?", "retrieval_method": "INTELLIGENT", "generation_model": "SIMPLE"}'
```

<div dir="rtl">

مقدار `retrieval_method` نام یکی از اعضای `RetrievalMethod` و مقدار `generation_model` نام یکی از اعضای `GenerationModel` است.

## ارزیابی

این ارزیابی بررسی می‌کند که آیا بازیابی، جواب‌های درست را در متن زمینه‌ای که به مدل زبانی داده می‌شود قرار می‌دهد یا نه. همهٔ عددهای این بخش از فایل `evaluation/results/2026-10-09_summary.json` آمده‌اند. این فایل را اسکریپت‌های پوشهٔ `evaluation/` در commit `e5b5815` ساخته‌اند. اجرا در تاریخ ۲۰۲۶-۱۰-۰۹ (۱۷ مهر ۱۴۰۵) روی یک لپ‌تاپ ویندوزی و فقط با CPU انجام شد.

**سؤال‌ها.** اسکریپت `evaluation/make_questions.py` با seed ثابت ۴۲، ۵۶ سؤال از خود Hetionet می‌سازد. سؤال‌ها از ۷ قالب و از هر قالب ۸ سؤال هستند. شش قالب یک رابطه را دنبال می‌کنند:
- ژن‌های مرتبط با یک بیماری
- داروهای درمان یک بیماری
- ژن‌هایی که یک دارو به آن‌ها متصل می‌شود
- علائم یک بیماری
- بافت‌هایی که بیماری در آن‌ها بروز می‌کند
- عوارض جانبی یک دارو

قالب هفتم دو رابطه را دنبال می‌کند: ژن‌هایی که داروهای درمان یک بیماری به آن‌ها متصل می‌شوند. جواب‌های درست مستقیم از یال‌های گراف خوانده می‌شوند. هر سؤال بین ۳ تا ۳۰ جواب درست دارد. برای قالب دومرحله‌ای این عدد بین ۳ تا ۶۰ است.

**سیستم‌ها.**
- **GraphRAG** با سه روش بازیابی، همه با تنظیمات پیش‌فرض:
  - `INTELLIGENT`: جست‌وجوی هدایت‌شده با نوع رابطه
  - `BFS`: روش پیش‌فرض رابط وب
  - `ADAPTIVE`
- **خط مبنای RAG برداری** (`evaluation/baseline_rag.py`):
  - همهٔ یال‌های Hetionet به‌صورت متن، بر اساس گره و نوع رابطه گروه‌بندی می‌شوند؛ مثلاً «hypertension (Disease). Compounds that treat it: …».
  - نتیجه ۳۳۴٬۵۵۵ تکه‌متن تا ۴۰۰ کاراکتر است که با مدل `all-MiniLM-L6-v2` به بردار تبدیل می‌شوند.
  - تکه‌هایی که بیشترین شباهت کسینوسی را به سؤال دارند، تا سقف ۲٬۰۰۰ کاراکتر کنار هم گذاشته می‌شوند. این سقف برابر با تنظیم `max_context_length` در GraphRAG است.

**معیارها.** کلید API برای مدل زبانی در دسترس نبود. برای همین فقط بازیابی ارزیابی شد و کیفیت پاسخ‌ها سنجیده نشد.
- *بازیابی در ۲٬۰۰۰ کاراکتر اول*: سهم جواب‌های درستی که در ۲٬۰۰۰ کاراکتر اول متن زمینه آمده‌اند. با این معیار همهٔ سیستم‌ها در اندازهٔ یکسان مقایسه می‌شوند.
- *بازیابی در کل متن*: همان سهم، ولی در کل متن زمینه.
- *نرخ اصابت*: سهم سؤال‌هایی که دست‌کم یک جواب درست در متن زمینه دارند.
- *بازیابی گره*: سهم جواب‌های درست در میان گره‌هایی که GraphRAG پیش از ساخت متن زمینه بازیابی کرده است.

سقف زمانی هر سؤال ۱۰ دقیقه بود و هیچ سؤالی به آن نرسید.

</div>

| System | n | Recall in first 2,000 chars | Recall in full context | Hit rate | Node recall | Mean context (chars) | Mean latency (s) |
|---|---|---|---|---|---|---|---|
| GraphRAG `INTELLIGENT` | 56 | 31.3% | 31.9% | 57.1% | 31.4% | 55,876 | 57 |
| GraphRAG `BFS` | 56 | 13.1% | 13.1% | 35.7% | 12.9% | 4,741 | 6.5 |
| GraphRAG `ADAPTIVE` | 56 | 5.4% | 5.4% | 23.2% | 4.9% | 1,734 | 9.2 |

### محدودیت‌ها

- **طراحی بنچمارک به نفع خط مبناست.** سؤال‌ها و تکه‌متن‌های خط مبنا هر دو از همان یال‌های Hetionet ساخته شده‌اند. سرتیتر تکه‌ای مثل «uterine cancer (Disease). Compounds that treat it:» تقریباً همان عبارت سؤال است. به همین دلیل سؤال‌های تک‌رابطه‌ای برای بازیابی برداری تقریباً ایده‌آل‌اند. این ارزیابی بازیابی روی محتوای خود Hetionet را می‌سنجد، نه روی متن آزاد. وقتی جواب در تکه‌های زیادی پخش شده باشد، یعنی در قالب دومرحله‌ای، خط مبنا به ۱۶.۴٪ می‌رسد که کمی پایین‌تر از ۱۹.۳٪ روش `INTELLIGENT` است.
- **خطاهای اصلی GraphRAG از تطبیق موجودیت و تشخیص نوع سؤال است، نه از جست‌وجوی گراف.** بررسی گره‌های تطبیق‌داده‌شده سه خطای تکراری را نشان داد:
  - کلمه‌های عمومی به گره‌های بی‌ربط تطبیق داده می‌شوند. «genes» و «compounds» به فرایندهای Gene Ontology، «symptoms» به یک عارضهٔ جانبی و «effects» به یک مسیر زیستی وصل می‌شوند.
  - نام بیماری‌های چندکلمه‌ای فقط بخشی تطبیق داده می‌شوند. «uterine cancer»، «lung cancer» و «larynx cancer» همه به گرهٔ عمومی *cancer* می‌رسند.
  - برخی عبارت‌بندی‌ها در قاعده‌های تشخیص نوع سؤال جا نمی‌افتند. «Which genes does X bind?» و «In which anatomical structures does X localize?» در دستهٔ *general* قرار می‌گیرند. همین بازیابی ۰٪ و ۸٪ در این قالب‌ها را توضیح می‌دهد.
- **متن زمینهٔ `INTELLIGENT` محدودیت طول را رعایت نمی‌کند.** میانگین طول آن ۵۵٬۸۷۶ کاراکتر و بیشینه‌اش ۱۶۱٬۵۱۳ کاراکتر است، در حالی که تنظیمات ۲٬۰۰۰ کاراکتر است. با بریدن متن در ۲٬۰۰۰ کاراکتر، بازیابی‌اش تقریباً تغییری نمی‌کند، چون گره‌های مرتبط اول فهرست آمده‌اند. بخشی از قالب‌های متن زمینه به فارسی نوشته شده‌اند.
- **بازیابی روی گراف کامل کند است.** روش `INTELLIGENT` روی CPU حدود ۵۷ ثانیه برای هر سؤال طول می‌کشد. در طول این ارزیابی دو اصلاح انجام شد که خروجی را تغییر نمی‌دهند: ساختن فقط چند کوتاه‌ترین مسیر اول، و پیمایش نکردن همسایه‌ها در آخرین سطح DFS. این دو اصلاح بدترین حالت حدود یک ساعت برای یک سؤال را حذف کردند. خط مبنا در ۰.۰۴ ثانیه پاسخ می‌دهد، ولی فقط بعد از یک بار تبدیل کل پیکره به بردار که روی CPU حدود ۲.۵ ساعت طول کشید.
- **دو روش بازیابی ارزیابی نشدند.** `KG_SEARCH` و `N_HOP_RETRIEVAL` روی سؤال‌های آزمایشی هیچ گره‌ای برنگرداندند. به نظر می‌رسد به اجزایی وابسته‌اند که اینجا راه‌اندازی نشده‌اند، مثل یک مدل زبانی یا یک نمایهٔ جست‌وجو.
- **نمونه کوچک و قالب‌محور است.** بنچمارک ۵۶ سؤال دارد و فقط یک بار اجرا شده است. سؤال‌ها نام دقیق موجودیت‌های Hetionet را دارند. سؤال‌های واقعی کاربران برای هر دو سیستم سخت‌تر خواهد بود.
